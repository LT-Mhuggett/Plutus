### A — the search path had no exception guard, and FOCUS ALONE rebuilt the list

⚠ **My first theory was wrong; the real cause is plainer.** `InitItems` wraps its `RebuildGroups()`
call in a try/catch. **The search path did not.** Identical code was survivable on load and fatal on
a keystroke — anything escaping reached the MAUI dispatcher as an unhandled exception and took the
process with it.

⚠ **And clicking in was enough.** A MAUI `SearchBar` on WinUI writes `Text` on FOCUS, moving it from
`null` to `""` — a change as far as `SetProperty` is concerned. So merely clicking into the box
rebuilt the whole grouped collection under a rendered `CollectionView`, before a character was typed.

Three changes: blank/null `SearchText` is normalised so focus is a no-op; `RebuildGroups` is
guarded; and `ItemGroups` is now **replaced wholesale** rather than `Clear()`-then-`Add()` — one
notification instead of a Reset plus N Adds against a grouped view.

### B — nothing anywhere gated a SALE on the day being open

⚠⚠ **CORRECTION TO WHAT I FIRST TOLD MATT: the sale WAS captured.** It committed locally, drained
normally, and the **server accepted it as 201 Recorded** — against a day already counted and banked.
The day-closed gate existed only on the **cash-event** path, till and server. The sales path never
asked.

⚠ **That is worse than losing it.** A lost sale is one problem; a sale added to a reconciled day
means the Z-read, the banking and the platform's figures disagree **for ever**, with nothing
flagging it. It surfaces weeks later as an unexplained discrepancy.

Gated in `CheckoutCommit.CommitAsync` — every sale and refund passes through it, and it already owns
the "refuse rather than record something wrong" decision. ✅ **The server now has its own gate too** — `ValidateDayNotClosedAsync` in `SalesIngestService`,
deployed as backend 1.10.0. ⚠ **QUARANTINED (202), not rejected**: the sale is real, somebody paid
and left with the goods, so it must not vanish — quarantine keeps the money visible and puts it in
front of a person. `OutboxPusher` treats 202 as terminal, so nothing loops.

⚠ **Two gates, one rule, and they protect different things.** The till's refuses before money is
taken, with the basket intact — that protects the OPERATOR. The server's protects the LEDGER,
because a till cannot be the only thing enforcing a rule about the platform's own books: an older
build, a replayed queue or a second device on the same till all reach the endpoint without passing
through the till's check.

### C — a dangling basket selection incremented a ghost

⚠ `SelectedBasketRecord` is bound to the basket list's selection and **was not cleared when the
basket emptied after a sale**. It kept pointing at the `BasketItem` for the line just sold — an
object no longer in `Basket`. Scanning that item matched it, incremented a **detached object**, and
added nothing. No error, no line, and the scan box cleared as though it had worked.

⚠ **It could only ever affect the item just sold** — exactly what Matt hit, and exactly what makes it
look like the item is broken rather than the till.

Guarded on `Basket.Contains(...)` so it is structurally impossible however the selection comes to
dangle, and the selection is nulled wherever its line goes away. ⚠ **The same bug is in
`Plutus.Frontend.ClientUI`** and is fixed there too — ⚠ **but that project will not build from the
CLI on this box** (its Windows target is gated on Visual Studio's MSBuild), so that edit is
**verified by reading, not by a compile.**

The functionality needs to be the same." | ⚠⚠ **THEY ALREADY WORK** — a test now proves £4 then £6 settles a £10 basket as two tenders. An amount smaller than the balance is ACCEPTED and the loop asks again for the rest. So the capability was never missing: nothing on the screen SAID the second prompt was the rest of the same sale, and until 1.42.0 a silent refusal mid-way made it look like an error. ⚠ Whether that is now obvious enough is Matt's call. | **G** | ⚠ **Refunds must offer ONLY the tender the sale was paid with.** "If it was a card payment, needs to go back to card." | ✅ **Fixed in 1.43.0.** `TillTenders.OfferedForRefund` filters the sheet to the tenders on the ORIGIN sale, read from this till's own stored payload (no network — a refund must work with the line down). ⚠ A SPLIT sale offers both. ⚠ An UNKNOWN origin (cross-till, or older than local history) offers everything — a guard rail, not a lock; refusing there would block a legitimate refund over a fact the till does not have. ⚠ So does an origin paid with something the till no longer offers, or the operator is trapped with no button. 8 tests, 3 mutations |
| **H** | **Stock write-offs are not reported anywhere.** "Where is this captured? I need a report on the portal (that will then be reflected in all tills) that shows stock adjustments" | The LEDGER already records every movement with its reason and actor (`StockMovement`). What is missing is a portal REPORT over it |
| **I** | **Z-close variance is not flagged.** Open £150, spend £20, close £110 → should be flagged, and there should be a portal report/warning for a till that closed short | ✅ **Fixed in till 1.45.0 + backend 1.11.0 + portal 1.4.0.** ⚠ **The arithmetic was never missing** — the platform has computed expected-vs-counted since WP9 and Banking has shown it in red since §9.2. What was missing was anyone being TOLD: the till kept the POST's status code and **discarded the response body**, which is the only place either figure exists, so a drawer £20 short was accepted with a 201 in silence. Now recorded on the local row (schema **v6**) and shown on the Cash line and in the summary header — red, with SHORT/OVER and Plutus's expected figure. ⚠ **A new rule fell out of it: the Z now WAITS for its own day's sales.** Expected = float + **cash takings** + ins − outs, so a Z pushed ahead of queued sales reports a shortage equal to every penny not yet sent — a till that traded £400 through an outage would tell the operator who counted correctly that they were £400 down. And the Z is terminal server-side, so it would also land the day's real sales in quarantine behind their own close. ⚠ Portal: a **⚠ Drawers out of balance** pill, 7-day window, **short and over summed SEPARATELY** — netting them would report one till £300 short and another £300 over as a quiet week. ⚠ **The pill's TSX is unbuilt** — no Node on this machine; it compiles on the Mac with the other web work |

missing is a SCREEN that offers them, or a SENTENCE that explains them. That is the same shape as
every previous hand-run: the components exist and nothing calls them.

⚠ **J and N are that shape at its purest, and N is the warning.** The cadence knew the queue had
drained and the platform knew the day's takings; in both cases the fact was correct and no screen

announces itself. N — a takings total frozen at sign-in — was found only because I went looking for
siblings of J, and it would never have been reported at all, because a wrong total looks exactly
like a right one. **When a redraw bug turns up, search for the others straight away.** The one that
gets reported is rarely the one that costs the most.
