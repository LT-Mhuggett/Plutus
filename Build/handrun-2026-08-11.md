### A — the search path had no exception guard, and FOCUS ALONE rebuilt the list

⚠ **My first theory was wrong; the real cause is plainer.** `InitItems` wraps its `RebuildGroups()`
call in a try/catch. **The search path did not.** Identical code was survivable on load and fatal on
a keystroke — anything escaping reached the MAUI dispatcher as an unhandled exception and took the
process with it.

⚠ **And clicking in was enough.** A MAUI `SearchBar` on WinUI writes `Text` on FOCUS, moving it from
`null` to `""` — a change as far as `SetProperty` is concerned. So merely clicking into the box
rebuilt the whole grouped collection under a rendered `CollectionView`, before a character was typed.

Three changes: blank/null `SearchText` is normalised so focus is a no-op; `RebuildGroups` is
guarded; and `ItemGroups` is now **replaced wholesale** rather than `Clear()`-then-`Add()` — one
notification instead of a Reset plus N Adds against a grouped view.

### B — nothing anywhere gated a SALE on the day being open

⚠⚠ **CORRECTION TO WHAT I FIRST TOLD MATT: the sale WAS captured.** It committed locally, drained
normally, and the **server accepted it as 201 Recorded** — against a day already counted and banked.
The day-closed gate existed only on the **cash-event** path, till and server. The sales path never
asked.

⚠ **That is worse than losing it.** A lost sale is one problem; a sale added to a reconciled day
means the Z-read, the banking and the platform's figures disagree **for ever**, with nothing
flagging it. It surfaces weeks later as an unexplained discrepancy.

Gated in `CheckoutCommit.CommitAsync` — every sale and refund passes through it, and it already owns
the "refuse rather than record something wrong" decision. ✅ **The server now has its own gate too** — `ValidateDayNotClosedAsync` in `SalesIngestService`,
deployed as backend 1.10.0. ⚠ **QUARANTINED (202), not rejected**: the sale is real, somebody paid
and left with the goods, so it must not vanish — quarantine keeps the money visible and puts it in
front of a person. `OutboxPusher` treats 202 as terminal, so nothing loops.

⚠ **Two gates, one rule, and they protect different things.** The till's refuses before money is
taken, with the basket intact — that protects the OPERATOR. The server's protects the LEDGER,
because a till cannot be the only thing enforcing a rule about the platform's own books: an older
build, a replayed queue or a second device on the same till all reach the endpoint without passing
through the till's check.

### C — a dangling basket selection incremented a ghost

⚠ `SelectedBasketRecord` is bound to the basket list's selection and **was not cleared when the
basket emptied after a sale**. It kept pointing at the `BasketItem` for the line just sold — an
object no longer in `Basket`. Scanning that item matched it, incremented a **detached object**, and
added nothing. No error, no line, and the scan box cleared as though it had worked.

⚠ **It could only ever affect the item just sold** — exactly what Matt hit, and exactly what makes it
look like the item is broken rather than the till.

Guarded on `Basket.Contains(...)` so it is structurally impossible however the selection comes to
dangle, and the selection is nulled wherever its line goes away. ⚠ **The same bug is in
`Plutus.Frontend.ClientUI`** and is fixed there too — ⚠ **but that project will not build from the
CLI on this box** (its Windows target is gated on Visual Studio's MSBuild), so that edit is
**verified by reading, not by a compile.**

## ⚠⚠ Note — writing H's test found a fault I had shipped into the test host

`RolePermissionReconciler` (added 2026-08-11 so permissions reach a tenant on BOOT, after Matt asked
why a manual seed step was needed at all) is a `BackgroundService` that **enumerates `Tenants` on
startup**. That is right in production. On the integration host it is not: `PlutusAppFactory` runs
every context on **one shared in-memory SQLite connection**, which is single-writer and not
thread-safe, and the reconciler's first query races the startup `EnsureCreated`.

⚠ **The symptom points nowhere near the cause.** It surfaces as
`SQLite Error 1: 'no such table: Tenants'` wrapped in *"a transient failure — consider enabling
`EnableRetryOnFailure()` on the `UseMySql` call"*, which reads as a connection-pool problem in a
suite that has no pool and no MySQL.

⚠ **And it was already intermittent.** The factory has always removed three hosted services for
exactly this reason and the reconciler was never added to the list, so whether it bit depended on
which class booted the host and how quickly its first request arrived. The suite stayed green until
`StockAdjustmentReportE2eTests` shifted the timing and took out **all eight** of its tests at once —
including two that touch almost no data, which is what gave it away. Now removed, with the reason
written where the next person will read it.

⚠ **The lesson is the one this file keeps repeating.** A green suite proves the components work; it
does not prove the harness is sound. This had been latent for hours behind 161 passing tests.
